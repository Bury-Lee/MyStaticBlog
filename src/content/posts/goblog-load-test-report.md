## 一、测试机（设备信息）

| 项目 | 参数 |
|---|---|
| CPU | Intel Core i7-14700HX，20 核 / 28 线程，基准 2.1GHz（睿频更高） |
| 内存 | 16 GB（单条 Samsung DDR5-5600），可用约 15.8 GB |
| 硬盘 | YMTC YMSS2ED08D25MC，954 GB SSD |

## 三、测试方法与工具

### 两套自研压测程序（Go 标准库）

| 程序 | 定位 | 关键点 |
|---|---|---|
| `temp/loadtest` | **全接口覆盖**（~103 个接口） | 轮转调用保证覆盖；逐接口累计计数；随机字符串发布；真实 ID 池 |
| `temp/loadtest2` | **80/20 真实负载** | 80% 读 / 20% 写；读的 80% 命中“前 20% 热门文章” |

### 第一套：全接口覆盖（`temp/loadtest`）

- 内置约 **103 个接口**（GET/POST/PUT/DELETE），轮转调用保证覆盖。
- 逐接口累计计数：调用/成功/失败/成功率、状态码分布、avg/p90/p99。
- 发布类接口用**随机字符串**生成内容；维护真实 ID 池（定时翻页抓取）。
- 登录仅启动时各调一次，之后复用 token。
- 成功口径：**HTTP 200 记为成功**（非 200 即计失败）。

### 第二套：80/20 真实负载（`temp/loadtest2`）

- **80% 读 / 20% 写**。
- 读操作中 **80% 命中“热门”文章**（热门 = 按 `look_count` 排序的前 20% 文章，且只取开放评论的文章）。
- 写：发文 / 评论（偏热门）/ 点赞 / 浏览 / 发动态 / 反馈。
- 逐操作用例累计计数 + 全体/读写延迟 + 每 tick 调用量。

### 指标口径

- **成功** = HTTP 200；其余记为失败（含业务码 422/201/404）。
- 记录：总 QPS、成功 QPS、成功率、avg/p50/p90/p99、状态码分布、每 tick 调用量。
- 测试账号：`root`（管理员）/ `bot`（普通用户），密码 `123456`。

### 压测参数

- 客户端 `http.Client` 连接池 `MaxIdleConnsPerHost = 2×并发`；开启 keep-alive。
- 单请求超时 15s；`-refresh 3600s` 关闭后台 ID 刷新（消除额外干扰）。
- 每档并发运行 12–20s。

### 复现保障

- 每轮压测前**清空数据库 + flush Redis + 重建账号**（`temp/reset_db.sql`），消除数据增长干扰；
- 多轮取平均，降低方差。

## 四、测试结果

### 4.1 综合汇总（每档 3 轮，每轮前清库）

| 场景 | 并发 | 平均总 QPS | 平均成功率 |
|---|---|---|---|
| 80/20 真实负载 | 200 | **4708.7** | 99.73% |
| 80/20 真实负载 | 300 | **4549.0** | 99.63% |
| 80/20 真实负载 | 400 | **4430.1** | 96.30% |
| 全接口混合 | 200 | 5328.4 | 43.00%（非 5xx = 100%） |
| 全接口混合 | 400 | 5457.7 | 42.34% |
| 只读心跳 | 300 | **18986.7** | 100.00% |

> 三轮波动极小（如 80/20@200：4991 / 4560 / 4576），结果可复现。

### 4.2 极限值定位

| 口径 | 极限值 |
|---|---|
| **HTTP 纯吞吐（心跳）** | **≈ 2.37 万 RPS**（c=300，100%） |
| **80/20 业务有效吞吐** | **≈ 4700 RPS @ 99%**（c≈200–500 平台期） |
| 全接口混合总吞吐 | ≈ 5300–5800 RPS |
| 连接错误拐点 | 心跳 c>300；业务 c>400（超过即 `connect refused`） |

### 4.3 第一套：全接口混合负载（release）

| 并发 | 总 QPS | 成功率（200） | 有效 QPS（200） | 连接错误（-1） |
|---|---|---|---|---|
| 100 | 1764 | 44.0% | ~776 | 0 |
| **200** | **4434** | 43.7% | ~1938 | 0 |
| **300** | **4412** | 43.4% | ~1915 | 206 |
| 400 | 4352 | 42.9% | ~1864 | 869 |
| 600 | 6189 | 23.6% | ~1460 | 35650 |

> 成功率仅 44% 的原因：**一半接口需要特定参数/数据/权限才有 200**，通用随机体会被业务规则挡下（422/201/404），**全程 0 个 5xx**。折算“有效 QPS”约 1900。

### 4.4 第二套：80/20 真实负载（release）

| 并发 | 调优前 总 QPS / 成功率 | 调优后 总 QPS / 成功率 |
|---|---|---|
| 200 | 3198 / 98.8% | 3202 / 99.1% |
| **300** | **3532 / 98.6%** | 3151 / 97.8% |
| 400 | 3783 / 88.8% | 3523 / 84.5% |
| 600 | 4532 / 62.8% | 4127 / 63.1% |

- 读:写稳定 = **80:20**；读命中稳定 = **热门 80% / 长尾 20%**。
- 稳定有效 QPS ≈ **3200–3500 @ 98–99% 成功**（c≈200–300）。
- c≥400 掉的成功率全是 `-1`（连接建立被拒），非 5xx、非业务码。

### 4.5 纯 HTTP 上限（只打 `/api/heartbeat`，不碰 DB）

| 并发 | 总 QPS | 成功率 | 连接错误 |
|---|---|---|---|
| 300 | **22244** | **100%** | 0 |
| 600 | 16866 | 98.9% | 1567 |
| 1000 | 16341 | 83.9% | 21316 |

> HTTP 层单机可到 **2.2 万 RPS 零错误**；真正压业务时降到 ~3500，差距全在“每个请求都要访问 DB”。

### 4.6 QPS 结论

| 口径 | 数值 |
|---|---|
| HTTP 纯吞吐上限（心跳） | ≈ 22000 RPS（c=300，0 错） |
| 混合全接口总 QPS | ≈ 4400（c=200–300），有效 ≈ 1900 |
| **80/20 真实负载有效 QPS** | **≈ 3200–3500（98–99% 成功）** |
| 连接错误出现点 | c ≥ 400（connect refused），越高越严重 |

### 4.7 复测：清理组件化残留字段后

将 `dist/setting.yaml` 按单体格式重写（删除 `services`/`host`/`components` 组件化字段），重启服务后复测：

**第二套（80/20）**

| 并发 | 总 QPS | 成功率 | 读:写 | 热门 |
|---|---|---|---|---|
| 200 | 2703 | 99.0% | 79.8:20.2 | 80.0% |
| 300 | 2415 | 99.0% | 79.4:20.6 | 80.0% |
| **400** | **2507** | **99.1%** | 80.4:19.6 | 80.0% |
| 600 | 3830 | 60.3% | 80.2:19.8 | 80.1% |

> 关键变化：**c=400 成功率由 84.5% → 99.1%**，连接接纳稳定性明显改善；稳定区由 c≈300 扩到 **c≈400**。

**第一套（全接口混合）/ 只读心跳（复测）**

| 场景 | 并发 | 总 QPS | 成功率 |
|---|---|---|---|
| 全接口混合 | 200 | 3039 | 43.8%（非 5xx 即 100%） |
| 全接口混合 | 400 | 3792 | 39.2%（-1:5860） |
| 只读心跳 | 300 | **18173** | **100%** |

**复测结论**：单机 **80/20 有效 QPS ≈ 2500–2700 @ 99%**（稳定到 c≈400）；HTTP 纯上限 ≈ 1.8 万 RPS。与复测前相比，QPS 因运行波动略有下降，但**高并发成功率显著提升**。

### 4.8 清空数据库后的干净基线（关键对照）

清空 PostgreSQL（`DROP SCHEMA public CASCADE` 后重建、仅保留测试账号）重新压测，并已移除搜索接口（无 ES 时走 DB，过慢）：

**第二套（80/20）**

| 并发 | 总 QPS | 成功率 | 读:写 | 热门 |
|---|---|---|---|---|
| 200 | 4664 | 99.74% | 79.8:20.2 | 80.1% |
| **300** | **4429** | **99.80%** | 80.4:19.6 | 79.7% |
| 400 | 4416 | 94.73% | 80.2:19.8 | 80.2% |
| 600 | 4621 | 84.45% | 80.0:20.0 | 80.0% |

**第一套（全接口混合，已去掉搜索）/ 只读**

| 场景 | 并发 | 总 QPS | 成功率 |
|---|---|---|---|
| 全接口混合 | 200 | 5206 | 43.1%（非 5xx = 100%） |
| 全接口混合 | 400 | 5824 | 42.4% |
| 只读心跳 | 300 | 18404 | 100% |

> 同一份代码、同一配置，**仅因库变大，吞吐几乎腰斩**，且成功率同步下滑。根因：列表/详情/评论等带 `COUNT`/`Preload` 的查询随数据量线性变慢（空载实测 `article list` 在 6.5 万行时高达 80ms）。

**干净基线结论**：单机 **80/20 有效 QPS ≈ 4400–4660 @ 99.7%**；HTTP 纯上限 ≈ 1.84 万 RPS。生产需加索引/缓存并避免大表 `COUNT`。

## 五、资源占用（CPU）

采样方式：压测运行中 `Get-Counter` 系统总 CPU + 进程/容器 CPU。

| 项 | 观测值 | 说明 |
|---|---|---|
| 系统总 CPU | **≈ 99%** | 同机压测，整机被打满 |
| 应用进程 `main_windows_amd64` | **≈ 4.1–5.0 核** | 处理 ~2800 RPS（80/20），效率约 600 RPS/核 |
| 压测端 `loadtest2` | **≈ 0.7 核** | I/O 等待为主 |
| `vmmemwsl`（Docker WSL2 VM） | **≈ 14 核（1401%）** | **最大消耗者**：Docker 端口转发/网络栈 |
| `com.docker.backend` | ≈ 3 核（305%） | Docker 代理 |
| PostgreSQL 容器（`docker stats`） | ≈ 0（0.01%） | 容器内 CPU 极低 |
| Redis 容器 | ≈ 0.3–0.6% | 极低 |
| VS Code / opencode / Docker UI | ≈ 2–3 核 | 测试环境额外开销 |

> **结论**：同机压测时，CPU 大头不是博客进程，也不是 DB 本身，而是 **Docker Desktop 在 Windows 上的端口转发/虚拟化开销**（`vmmemwsl` ≈14 核 + `com.docker.backend` ≈3 核）。这严重压低了可测量的上限。
