## 一、网络分层模型：为什么需要分层？

构建一个全球互联的通信网络，要解决的问题极其庞杂：物理信号传输、相邻节点通信、跨网络寻址、端到端可靠传输、应用协议解析……如果把这些全部揉在一起，任何一个小改动都可能牵一发而动全身。

**分层**就是把这一大坨问题拆成若干层，每层只解决自己那一层的问题，并为上层提供清晰的服务接口。

### 1. 经典四层模型（TCP/IP 模型）

![经典四层结构](/images/cs144/image-1.png)

| 层级 | 名称 | 核心协议 | 职责 |
|:---|:---|:---|:---|
| 第四层 | **应用层** | HTTP、WebSocket、DNS、SMTP | 为应用进程提供网络服务 |
| 第三层 | **传输层** | TCP、UDP | 进程到进程的（可靠/不可靠）数据传输 |
| 第二层 | **网络层** | IP | 端到端的寻址与路由（逐跳转发） |
| 第一层 | **链路层** | 以太网、Wi-Fi | 相邻节点间的帧传输 |

### 2. OSI 七层模型：曾经更细致的理想划分

![OSI 七层结构](/images/cs144/image-2.png)

OSI（Open Systems Interconnection）七层模型将通信过程划分得更加细粒度，在四层的基础上增加了**会话层**和**表示层**。然而，这个模型在实际落地时过于理想化——现实中的协议栈（尤其是 TCP/IP）并不严格对应这七层。如今它更多作为**教学参考框架**存在，真正统治互联网的是四层 TCP/IP 模型。

### 3. TCP 与 UDP：传输层的两条路径

| 特性 | TCP | UDP |
|:---|:---|:---|
| 连接模型 | **面向连接**（需三次握手建立连接） | **无连接**（直接发送） |
| 可靠性 | **可靠**（确认、重传、排序） | **不可靠**（尽力而为，无确认） |
| 顺序保证 | 有序交付 | 不保证顺序 |
| 适用场景 | 文件传输、网页浏览、邮件 | 视频直播、语音通话、DNS 查询 |

> 在传输层之上，应用层可以进一步构建更丰富的协议，如 HTTP、WebSocket、RPC 等——这些协议的差异在于**语义**（请求/响应、全双工、远程过程调用），但都依赖 TCP 或 UDP 提供的基础传输能力。

### 4. 分层思想的精髓

![网络传输](/images/cs144/image.png)

每层之间**没有交叉通信**，只有两种交互模式：

- **垂直方向**：向下调用下层提供的 API，向上为上层提供封装好的服务。
- **水平方向**：同一层之间通过协议"对话"（如 TCP 段的对端通信、IP 包的对端路由），但实际数据仍然要经过下层传递。

这种"层层抽象"让构建网络应用变得职责清晰、易于扩展——写 HTTP 应用的开发者不需要关心路由表怎么查，路由器厂商也不需要理解 HTTP Header 的格式。

## 二、IP 协议：互联网的"邮政系统"

IP（Internet Protocol）是网络层的核心协议，也是整个互联网体系中**唯一无可替代**的一层。IP 的地位可以用一句话概括：

> **IP 是互联网的"窄腰"**——上层可以有 TCP、UDP、SCTP 等各种传输协议，下层可以有以太网、Wi-Fi、4G/5G 等各种链路技术，但中间必须统一走 IP。

### 1. IP 的核心特性

![IP 协议概述](/images/cs144/image-3.png)

| 特性 | 说明 |
|:---|:---|
| **独立选路（Individually Routed Packets）** | 每个 IP 数据包独立选择转发路径，不依赖同一流中其他包的路径 |
| **逐跳路由（Hop-by-hop Routing）** | 每个路由器只根据目的地址决定下一跳，不预先指定完整路径（区别于源路由） |
| **不可靠（Unreliable）** | 数据包可能丢失、损坏、乱序——IP 只尽力而为（Best Effort），不保证送达 |
| **无连接（Connectionless）** | IP 层不为通信双方维护连接状态，每个包独立处理 |
| **无每流状态（No Per-flow State）** | 路由器不需要为每个数据流维护内部状态信息，这极大简化了网络核心的复杂度 |

IP 的行为类似于传统**邮政系统**：

- 寄信时只填写收件人地址，不指定邮局内部如何分拣。
- 每封信可能走不同的路线，到达顺序可能与发送顺序不一致。
- 不保证一定送达（可能丢失），不保证送达时间。
- 邮局不需要为"你"这个寄件人维护任何特殊记录。

<details>
<summary>补充：为什么 No Per-flow State 这么重要？</summary>

想象一下，如果路由器需要为每个经过它的 TCP 连接都维护一份状态（序列号、确认号、拥塞窗口……），那么一个核心路由器可能承载数百万并发连接，内存会瞬间被耗尽。

No Per-flow State 意味着路由器对每个数据包的处理是**无记忆的**——看一眼目标 IP，查路由表，丢出去。连接状态完全由**端节点**（发送方和接收方）维护，这就是著名的**端到端原则**（End-to-End Principle）：只有通信的端点才有足够的信息来保证可靠性，网络中间节点应该保持简单。

</details>

### 2. IPv4 数据报格式详解

![IPv4 数据报](/images/cs144/image-4.png)

IPv4 数据报由**首部**（20~60 字节）和**数据载荷**组成。以下是首部各字段的完整解析：

---

#### 版本（Version）—— 4 比特

- **作用**：标识 IP 协议版本，IPv4 固定为 `0100`（4）。
- **为什么放在最前面**：让网络设备在解析数据报的第一时间就知道用哪种协议格式来解读后续比特流。

---

#### 首部长度（IHL, Internet Header Length）—— 4 比特

- **作用**：表示 IP 首部的长度，以 **4 字节** 为单位。常见值为 `0101`（5），即 `5 × 4 = 20` 字节（无选项时）。
- **为什么要有**：因为首部有可选的"选项"字段，长度不固定。接收方需要这个字段来定位"数据从哪里开始"。

---

#### 区分服务（DSCP） + 显式拥塞通知（ECN）—— 8 比特

- **前 6 位（DSCP）**：用于服务质量（QoS），标记数据包的优先级（如语音、视频优先）。
- **后 2 位（ECN）**：用于网络拥塞通知，路由器在拥塞时标记此位，告知发送方减速而不必直接丢包。
- **意义**：让 IP 不仅能"尽力而为"地转发，还能提供差异化服务与拥塞控制预警。

---

#### 总长度（Total Length）—— 16 比特

- **作用**：表示整个 IP 数据报（首部 + 数据）的总字节数，最大 65535 字节。
- **与首部长度配合**：总长度 − 首部长度 = 数据载荷的长度，接收方据此完整提取包内容。

---

#### 标识（Identification）—— 16 比特

- **作用**：发送端为每个 IP 数据报分配的唯一 ID。当数据报因过大需要**分片**时，所有分片携带相同的标识号。
- **为什么要有**：接收方收到多个分片后，靠这个 ID 把属于同一原始数据报的分片归拢重组。

---

#### 标志（Flags）—— 3 比特

| 位 | 名称 | 含义 |
|:---|:---|:---|
| 第 0 位 | 保留 | 必须为 0 |
| 第 1 位 | **DF**（Don't Fragment） | 为 1 时，若包过大则直接丢弃并返回 ICMP 错误，不分片 |
| 第 2 位 | **MF**（More Fragments） | 为 1 表示后面还有分片，最后一个分片的 MF = 0 |

---

#### 片偏移（Fragment Offset）—— 13 比特

- **作用**：表示当前分片在原始数据报中的偏移量，以 **8 字节** 为单位。
- **为什么要有**：接收方重组时，必须知道每个分片的先后顺序和起始位置。13 位可覆盖最多 8192 个分片位置。

---

#### 生存时间（TTL, Time to Live）—— 8 比特

- **作用**：数据包每经过一个路由器（一跳），TTL 减 1。当 TTL 变为 0 时，路由器丢弃该包并发送 ICMP 超时消息。
- **为什么要有**：**防止数据包在网络环路中无限循环**。这也是 `traceroute` 工具的核心原理——通过逐步增大 TTL 来探测路径上的每一跳。

---

#### 协议（Protocol）—— 8 比特

- **作用**：指示 IP 数据载荷属于哪种上层协议。

| 值 | 协议 |
|:---|:---|
| `1` | ICMP |
| `6` | **TCP** |
| `17` | **UDP** |
| `89` | OSPF |

- **为什么要有**：接收主机完成 IP 层处理后，需要知道把数据交给内核中的哪个协议模块（TCP/UDP/ICMP）继续处理。

---

#### 首部校验和（Header Checksum）—— 16 比特

- **作用**：仅对 IP **首部**（不含数据）进行差错校验，使用反码求和算法。每经过一个路由器（TTL 变化），校验和必须重新计算。
- **为什么只校验首部**：为了提高转发效率。数据部分的校验交给上层（TCP/UDP）负责。如果首部校验失败，路由器直接丢弃——因为连目的地都不知道，无法转发。

---

#### 源/目的 IP 地址 —— 各 32 比特

- **源 IP 地址**：发送方地址，接收方用于回复，路由器也用于访问控制。
- **目的 IP 地址**：接收方地址，路由器根据它查路由表来决定下一跳。

---

#### 选项（Options）与填充（Padding）—— 0~40 字节

- **作用**：扩展功能，如记录路由（RR）、时间戳、严格/宽松源站选路。实际中因安全和性能原因很少使用。
- **为什么还要保留**：为 IP 协议预留扩展性，应对特殊网络需求（调试、多播、安全策略）。

---

### 字段速查总表

| 比特位 | 字段 | 长度 | 核心作用 |
|:---:|:---|:---:|:---|
| 0–3 | 版本 | 4 bit | 协议识别（IPv4） |
| 4–7 | 首部长度 | 4 bit | 定位数据起点 |
| 8–15 | 服务类型（DSCP + ECN） | 8 bit | QoS 与拥塞通知 |
| 16–31 | 总长度 | 16 bit | 数据报总大小 |
| 32–47 | 标识 | 16 bit | 分片归属标记 |
| 48–50 | 标志 | 3 bit | 控制分片行为 |
| 51–63 | 片偏移 | 13 bit | 分片位置排序 |
| 64–71 | TTL | 8 bit | 防止循环转发 |
| 72–79 | 协议 | 8 bit | 上层协议类型 |
| 80–95 | 首部校验和 | 16 bit | 头部完整性校验 |
| 96–127 | 源 IP 地址 | 32 bit | 发送方地址 |
| 128–159 | 目的 IP 地址 | 32 bit | 接收方地址 |
| 160+ | 选项 + 填充 | 可变 | 扩展功能（很少用） |

## 三、分组交换：网络通信的核心范式

### 1. 什么是分组交换？

**分组交换**（Packet Switching）是一种将用户数据分割为若干独立数据块（即**分组 / Packet**），每个分组独立地在网络中通过路由器逐跳转发，最终在接收端重新组装的通信方式。

![分组交换示意 1](/images/cs144/image-5.png)

![分组交换示意 2](/images/cs144/image-6.png)

### 2. 核心优势

- **统计复用**：来自不同用户或应用的分组可以交错地在同一条物理链路上并行传输，最大化利用带宽。
- **分布式路由决策**：每个路由器独立地为每个分组决定下一跳，避免了单点故障，增强了网络的鲁棒性。
- **职责分离**：交换机/路由器仅专注于数据分组的存储转发，无需维护端到端的连接状态——这简化了网络核心的功能。

### 3. 分组交换的深层思想：两个维度的解耦

分组交换之所以能支撑起今天的互联网规模，根本原因在于它实现了两个维度的**解耦**：

#### 垂直解耦：分层模型

不同层次之间各司其职：

- **物理层**：专注比特流的透明传输，把数据变成光/电信号。
- **数据链路层**：专注**相邻节点**间（单跳）的帧传输，交换机工作在这一层（根据 MAC 地址转发帧）。
- **网络层**：专注**端到端**（多跳）的寻址和路由，路由器工作在这一层（根据 IP 地址独立选路）。
- **传输层**：专注**进程到进程**的可靠通信，TCP 负责重传、排序、流量控制——只关心两端，不关心中间网络。

#### 水平解耦：控制平面与数据平面

分组交换将通信任务按性质拆分为两类：

| 平面 | 职责 | 特点 |
|:---|:---|:---|
| **数据平面** | 对每个分组执行"匹配 + 转发" | 高度重复、需要硬件高速完成 |
| **控制平面** | 通过路由协议交换信息，计算路由表 | 复杂、需要软件灵活处理 |

> 也就是说，网络把复杂的**路由决策**（控制平面）和简单重复的**分组转发**（数据平面）彻底解耦。这使得网络核心可以专注于高速转发，而路由策略的变化不影响转发性能。

> **分组交换的深层思想是对通信任务进行垂直与水平两个维度的解耦。**
>
> **垂直方向上，通过分层模型让物理传输、单跳转发、端到端路由和进程通信各司其职。**
>
> **水平方向上，则将用户数据流分离为独立分组，将通信任务分解为"控制平面"的复杂路由决策与"数据平面"的简单高速转发，最终实现网络的高效、灵活与可扩展。**

### 4. 数据封装与解封全过程

以浏览器发送一个 HTTP 请求为例，数据在每一层被逐层封装，经过路由器中转，最终在服务器端被逐层解封：

---

**发送端：逐层封装 ↓**

**第一层：应用层（HTTP）**
浏览器构建 HTTP 请求报文（请求行、Headers、Body），这时的数据叫**应用数据流**。

**第二层：传输层（TCP）—— 切段**

TCP 要做两件事：
1. **切分**：将连续的字节流切成多个适合网络传输的小块，叫 **TCP 段（Segment）**。
2. **封装**：给每个数据块加上 TCP 头，包含源端口、目的端口、序列号等控制信息。

**第三层：网络层（IP）—— 打包**
网络层给每个 TCP 段加上 IP 头，包含源 IP 地址和目的 IP 地址——此时数据叫 **IP 数据包（Packet）**。

**第四层：链路层（以太网）—— 成帧**
加上 MAC 帧头和帧尾（源/目的 MAC 地址），此时数据叫 **帧（Frame）**。成帧后，通过网卡转换成光电信号发送出去。

---

**中转站：路由器 —— 只换帧头，不拆包**

路由器收到帧后：
1. 拆掉 MAC 帧头和帧尾，看到 IP 包。
2. 根据目的 IP 查路由表，决定下一跳。
3. 重新封装成新的 MAC 帧（更换源/目的 MAC 地址）发出去。

> 路由器**只更换链路层帧头**，绝不切分或修改 IP 包的内容。如果路径上某一段的 MTU（最大传输单元）小于包长，路由器会直接丢弃该包并回传 ICMP 错误，由发送方主机根据 PMTUD（路径 MTU 发现）重新调整包大小。

---

**终点站：服务器 —— 逐层解封 ↑**

服务器从物理层收到信号后：
1. 拆掉 MAC 帧头帧尾，得到 IP 包。
2. 拆掉 IP 头，得到 TCP 段。
3. 根据序列号将 TCP 段重组成完整的应用数据流。
4. 交给应用层（HTTP 服务器）处理。

如果中间有 TCP 段丢失，接收方会根据序列号请求重传。

---

## 四、TCP 连接建立：三次握手

TCP 是面向连接的协议，在传输数据之前必须通过**三次握手**建立连接：

| 步骤 | 方向 | 报文类型 | 含义 |
|:---|:---|:---|:---|
| **第一步** | Client → Server | **SYN** | 客户端请求建立连接，携带初始序列号 |
| **第二步** | Server → Client | **SYN-ACK** | 服务器确认收到请求，同时发送自己的初始序列号 |
| **第三步** | Client → Server | **ACK** | 客户端确认收到服务器的同步信息，连接建立完成 |

三次握手后，双方都确认了对方的收发能力正常，随后可以开始传输数据。

<details>
<summary>为什么是三次，而不是两次或四次？</summary>

- **两次握手不够**：如果只有两次，服务器在回复 SYN-ACK 后就直接认为连接已建立，但它不知道客户端是否真正收到了自己的 SYN-ACK（可能丢包）。这会导致服务器为"半开连接"分配资源。
- **三次握手刚刚好**：第三次 ACK 让客户端确认收到了服务器的同步信息，同时让服务器知道客户端确实"活着"。至此双方都确认双向通信能力正常。
- **四次握手是多余的**：服务器的 SYN 和 ACK 可以合并为一条 SYN-ACK，没必要分开。

</details>

## 五、路由与子网

### 1. 路由表与默认路由

路由器内部维护一张**路由表**，记录着"目的网络 → 下一跳出口"的映射关系。当数据包到达时，路由器查找路由表：

- **有匹配条目**：按对应的下一跳转发。
- **没有匹配条目**：使用**默认路由（Default Route）**——通常指向一个上游的"默认网关"，如 `0.0.0.0/0`。

![网络地址分配](/images/cs144/image-7.png)

### 2. 子网掩码

**子网掩码**（Subnet Mask）是与 IP 地址配合使用的 32 位二进制数字，用于界定 IP 地址中**网络部分**和**主机部分**的分界线。

判断规则：

- 掩码中为 `1` 的位 → 对应 IP 地址的**网络部分**
- 掩码中为 `0` 的位 → 对应 IP 地址的**主机部分**

两台主机是否在同一局域网内，取决于——将它们各自的 IP 地址与子网掩码进行**按位与（AND）运算**后，得到的网络地址是否相同：

- **相同** → 同一局域网，可通过链路层直接通信（无需经过网关）。
- **不同** → 不同网络，需要通过路由器（网关）转发。

> 在 IPv6 中，这个概念不再叫"子网掩码"，而是叫**前缀长度（Prefix Length）**——前缀长度直接表示网络部分的位数，如 `/64` 表示前 64 位是网络前缀。

### 3. 最长前缀匹配

当路由表中存在多条都能匹配目标 IP 的记录时，路由器选择**子网掩码最长（前缀长度最长）**的那一条进行转发。

举例：

| 路由条目 | 匹配范围 | 下一跳 |
|:---|:---|:---|
| 路由 A | `10.1.0.0/16`（更宽泛） | 出口 X |
| 路由 B | `10.1.2.0/24`（更精确） | 出口 Y |

当目标 IP 为 `10.1.2.5` 时，它**同时**匹配路由 A 和路由 B。根据最长匹配原则，路由器选择路由 B（`/24` > `/16`），从出口 Y 转发。

> 前缀就像一个子网的"身份证号"，匹配前缀就等同于匹配了整个子网。最长匹配确保了数据包总是沿着**最精确、最具体**的路径被路由——这就像邮编越精确，分拣越准确。

## 六、ARP：地址解析协议

### 1. 为什么需要 ARP？

在网络通信中，IP 地址用于端到端的寻址，但当数据包到达"最后一跳"的局域网时，实际是通过 **MAC 地址**在链路层传输帧。这就需要一个机制将 IP 地址"翻译"为 MAC 地址——**ARP（Address Resolution Protocol）** 正是做这件事的。

> ARP 是网络层发现**与其直接相连的网络**中，与给定 IP 地址关联的 MAC 地址的机制。每一台主机和路由器都会在内存中缓存一份 **ARP 表**（IP → MAC 的映射），以减少重复查询。

### 2. ARP 报文格式

![ARP 数据包](/images/cs144/image-8.png)

ARP 报文**直接封装在以太网帧中**（没有 IP 头），结构非常简单：

| 字段 | 长度 | 说明 |
|:---|:---|:---|
| **硬件类型** | 2 字节 | 链路层协议类型，以太网 = `1` |
| **协议类型** | 2 字节 | 网络层协议类型，IPv4 = `0x0800` |
| **硬件地址长度** | 1 字节 | MAC 地址字节数，固定为 `6` |
| **协议地址长度** | 1 字节 | IP 地址字节数，固定为 `4` |
| **操作码** | 2 字节 | `1` = 请求，`2` = 应答 |
| **发送方硬件地址** | 6 字节 | 发送方的 MAC 地址 |
| **发送方协议地址** | 4 字节 | 发送方的 IP 地址 |
| **目标硬件地址** | 6 字节 | 目标的 MAC 地址（请求包中填全 `0`） |
| **目标协议地址** | 4 字节 | 目标的 IP 地址 |

### 3. 设计亮点："买一送一"

ARP 请求的设计非常巧妙——请求方在问"谁是 `10.0.0.2`？"的同时，也把自己的 MAC 地址和 IP 地址附上了。这种"买一送一"带来了两个好处：

- **目标主机**：收到请求后，直接用里面的信息生成应答包，并顺便把请求方的 IP-MAC 映射记入自己的缓存——省得后面再问一次。
- **局域网内的其他设备**：都可以趁机"偷窥"并记录发送方的映射信息，批量提升网络效率。

### 4. 完整工作流程

以主机 A（IP: `10.0.0.1`, MAC: `AA:AA`）请求主机 B（IP: `10.0.0.2`, MAC: `BB:BB`）的 MAC 地址为例：

**第一步：A 广播 ARP 请求**

| 字段 | 值 | 说明 |
|:---|:---|:---|
| 操作码 | `1` | 请求 |
| 发送方硬件地址 | `AA:AA` | A 的 MAC |
| 发送方协议地址 | `10.0.0.1` | A 的 IP |
| **目标硬件地址** | `00:00:00:00:00:00` | **未知，填全 0** |
| 目标协议地址 | `10.0.0.2` | 要查询的 IP |

**第二步：B 单播 ARP 应答**

| 字段 | 值 | 说明 |
|:---|:---|:---|
| 操作码 | `2` | 应答 |
| 发送方硬件地址 | `BB:BB` | **核心答案：B 的 MAC** |
| 发送方协议地址 | `10.0.0.2` | B 的 IP |
| 目标硬件地址 | `AA:AA` | 直接发给 A |
| 目标协议地址 | `10.0.0.1` | A 的 IP |

A 收到应答后，将 `10.0.0.2 → BB:BB` 写入 ARP 缓存，后续通信无需再次查询。

<details>
<summary>补充：ARP 的"悲伤历史遗留"</summary>

你可能想问：既然 IP 在互联网中唯一标识一台主机，为什么要引入另一套 MAC 地址，而不是直接使用 IP 地址进行链路层通信？

历史原因是：以太网（MAC 地址体系的来源）在 IP 之前就已被广泛部署，而 IP 在设计时需要运行在**多种**链路层技术上（以太网、令牌环、FDDI 等），不能绑定某一种地址格式。于是形成了"IP 在上、MAC 在下"的双层地址结构——IP 负责全局寻址，MAC 负责局域网内的实际传输。

这也解释了为什么 ARP 的报文格式设计了"硬件类型"和"协议类型"字段——不仅仅用于"以太网 + IPv4"的组合，理论上任何链路层和网络层的组合都可以用同一套请求/应答逻辑。

</details>
